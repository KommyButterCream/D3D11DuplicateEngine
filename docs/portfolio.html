이 엔진은 데스크톱 화면을 GPU 텍스처로 캡처해 다른 D3D11 디바이스가 바로 읽을 수 있는 형태로 내보내는 DLL 이다. 실제 사용처는 원격 데스크톱 스트리밍 서버로, 캡처 결과가 곧바로 NVENC 인코더로 넘어가 QHD 60 fps 로 송출된다.

설계에서 가장 많은 시간을 쓴 부분은 캡처 자체가 아니라 끊기지 않게 만드는 일이었다. Desktop Duplication 은 잠금화면, UAC 보안 데스크톱, 해상도 변경, 전체화면 전환, TDR, RDP 접속에서 일상적으로 접근 권한을 잃는다. 이것들을 모두 정상 경로로 흡수하는 것이 이 모듈의 핵심 가치다.

풀어야 했던 문제

기능 목록이 아니라, 설계를 강제한 제약들.

1. Desktop Duplication 은 수시로 끊긴다

AcquireNextFrame 이 DXGI_ERROR_ACCESS_LOST 를 돌려주는 상황은 오류가 아니라 Windows 의 평범한 동작이다. 사용자가 Win+L 을 누르거나 UAC 창이 뜨면 보안 데스크톱으로 전환되면서 duplication 객체가 무효화된다. 이걸 실패로 처리하면 화면 공유는 사용자가 비밀번호를 한 번 입력할 때마다 죽는다.

2. 캡처와 인코딩이 같은 컨텍스트를 쓰면 교착한다

D3D11 immediate context 는 스레드 안전하지 않아서 게이트로 직렬화해야 한다. 그런데 캡처와 인코더가 같은 디바이스를 공유하면 게이트도 하나가 되고, 인코더가 그 게이트를 쥔 채 드라이버 안에서 블로킹하는 순간 캡처가 통째로 멈춘다.

실측

QHD 60 fps 부하에서 실제로 이 교착이 재현됐다. 해법은 게이트를 정교하게 만드는 것이 아니라 디바이스를 아예 분리하는 것이었다 — 컨텍스트가 독립이면 순환 자체가 성립하지 않는다. 대신 캡처 결과를 건네줄 길이 필요해지고, 그것이 공유 프레임 풀이다.

3. 소비자를 기다리면 안 된다

실시간 스트리밍에서 붙들린 프레임은 값어치가 없다. 소비자가 밀렸을 때 캡처가 기다리면 지연이 누적되고, 그렇게 지켜낸 프레임은 어차피 이미 낡은 화면이다. 그래서 이 엔진은 모든 경합 지점에서 기다리는 대신 버리는 쪽을 택하고, 버린 사실을 카운터로 남긴다.

4. 정지 화면이 비용을 만들면 안 된다

duplication 은 마우스 커서만 움직여도 프레임을 돌려준다. 그대로 인코더에 넘기면 아무것도 바뀌지 않은 화면을 초당 60번 인코딩하게 된다. 이것을 걸러내는 것이 가장 비용 대비 효과가 큰 최적화였다.

코드 구조

파일 7개, 클래스 2개. 무엇이 무엇을 부르는가.

소유 방향을 한쪽으로 고정했다

엔진이 스레드를 소유하고, 스레드는 엔진의 ProcessCaptureFrame 을 부르기만 한다. 반대 방향 참조가 없어서 종료 순서가 자명해진다 — Shutdown 은 언제나 StopThread 로 시작한다.

스레드가 엔진 리소스를 계속 만지고 있으므로, 그 반대 순서로 지우면 해제된 객체를 참조하는 창이 열린다. 순서가 코드 한 줄로 강제된다는 것이 이 배치의 값어치다.

아키텍처와 스레드 모델

스레드는 둘뿐이고, 둘 사이에 락이 없다.

스레드는 둘

  • 캡처 스레드 (D3D11DuplicateThread) — 페이싱, duplication 획득, 슬롯 복사, 발행, 복구까지 전부. 상태 기계 전체가 이 스레드 하나 안에서 돈다.
  • 소비자 스레드 — 호출자의 스레드. GetLatestFrameHandle / ReleaseLatestFrameHandle 만 쓴다.

두 콜백(FrameCallback, CaptureEventCallback)은 모두 캡처 스레드에서 불린다. 여기서 블로킹하면 캡처 주기가 그대로 밀리므로, API 문서와 헤더 주석 양쪽에 이 제약을 명시했다.

동시성 모델

어디에 락을 쓰고 어디에 쓰지 않는가, 그리고 그 기준.

이 모듈은 락을 전부 없앤 설계가 아니다. 기다려야 하는 자리에는 커널 객체를 쓰고, 기다리면 안 되는 자리에만 원자 연산을 쓴다. 그 경계를 어디에 긋느냐가 설계의 대부분이었다.

왜 슬롯 선점에 락을 쓰지 않는가

락 자체가 느려서가 아니다. 소비자가 프레임을 붙잡고 있는 동안 생산자가 막히기 때문이다. 소비자는 그 텍스처로 인코딩이나 렌더링을 한다 — 수 밀리초 단위다. 그 시간이 캡처 주기에 그대로 실리면 캡처가 소비자 속도에 묶인다.

referenceCount 를 원자 카운터로 두면 생산자는 "이 슬롯은 쓸 수 없다" 는 사실만 읽고 다음 슬롯으로 넘어간다. 네 슬롯이 전부 막혀 있으면 그 프레임을 버린다 — 기다리는 선택지가 애초에 없다.

비동기가 무엇을 의미하는가

이 모듈에서 "비동기" 는 두 군데다. 성격이 다르다.

자리무엇이 비동기인가기다리는 쪽
GPU 복사CopyResource 는 명령을 큐에 넣을 뿐이다 소비자 — AcquireFrame 안에서 EVENT 쿼리로 확인
프레임 전달발행과 수신이 서로를 기다리지 않는다 아무도 — 최신 표식만 보고 각자 진행

앞은 GPU 와 CPU 사이의 비동기라 완료를 확인할 방법이 필요하다(쿼리). 뒤는 CPU 스레드 사이의 비동기라 순서만 지키면 된다(발행 순서 + 재확인). 둘을 같은 도구로 풀려고 하면 어느 한쪽이 과하거나 모자라게 된다.

큐를 쓰지 않는 이유

이 모듈에는 프레임 큐가 없다. 대신 4슬롯 풀 + 최신 표식이다. 큐는 "모든 항목이 처리된다" 를 전제하는 자료구조인데, 실시간 캡처에서는 그게 틀린 전제다 — 소비자가 밀리면 중간 프레임은 처리되면 안 된다.

풀 + 최신 표식은 그 성질을 자료구조 자체로 표현한다. 소비자는 항상 최신 것만 보고, 그사이 지나간 프레임은 버려지는 것이 아니라 애초에 관심 대상이 아니다. (인코더 쪽 EncodeFrameQueue 가 latest-only 큐로 같은 성질을 흉내내는 것과 대비된다 — 그쪽은 프레임 반납 콜백이 필요해서 큐 형태를 유지했다.)

락으로 같은 풀을 구현하면 어떻게 되는가

실제 슬롯 풀과 같은 모양을 세 가지로 구현해 비교했다 — (A) 장부 전체를 SRWLOCK 으로 감싸고 사용 구간에도 락을 쥐는 단순 구현, (B) 락은 장부만 지키고 사용 구간은 refCount 로 표시하는 구현, (C) 실제 구현 — CAS 선점 + 재확인.

실제 동작점 (생산자 60 fps, 소비자가 프레임당 2~8 ms 점유) — 생산자의 발행 소요 시간:

포화 상태 (생산자가 최대 속도로 발행, 소비자가 계속 수신) — 여기서 갈린다:

락 쪽 발행 처리량이 2.5배 높다. 그런데 소비자에게 도달한 프레임은 1/12 이다. 생산자가 락을 계속 다시 잡아 소비자를 굶긴 것이고, 발행한 51 M 중 98.3% 는 아무도 보지 않은 채 덮여 사라졌다.

이것이 락의 진짜 비용이다 — 느려서가 아니라 두 쪽을 하나의 자원에 묶어서, 부하가 걸리면 어느 한쪽이 상대를 굶긴다. 어느 쪽이 굶을지는 스케줄러가 정하므로 설계자가 통제할 수 없다.

락 없는 쪽은 생산자와 소비자가 서로를 막지 않으므로 발행량이 낮아 보여도 전달량이 11.9배 많다. 이 모듈이 실제로 사는 지점은 60 fps 라 위의 두 번째 표가 직접 발생하지는 않지만, 뷰어가 늘거나 소비자가 느려졌을 때 어느 쪽으로 무너지는지가 여기서 결정된다.

정직하게 — 절대량으로는 작다

프레임 풀 경로에서 원자 읽기는 프레임당 대략 13회다(발행 5회 + 수신 8회). 14.03 사이클 × 13 ≈ 180 사이클, 4.29 GHz 에서 약 42 ns. 60 fps 프레임 예산 16.7 ms 의 0.00025% 다.

즉 이 치환의 값어치는 이 모듈의 프레임 예산을 아낀 것이 아니다. 의미가 있는 곳은 (a) 초당 수만~수십만 회 도는 네트워크 엔진의 핫 경로, (b) 여러 스레드가 같은 플래그를 폴링하는 구간 — 위 표의 50배가 거기서 나온다. 이 모듈에서는 "읽기에 쓰기 명령을 쓰지 않는다" 는 규칙의 일관성이 얻은 것에 가깝다.

반대로 alignas(64) 캐시 라인 분리는 9.3배로, 절대량으로도 의미가 있다. 캡처 스레드가 매 프레임 카운터를 올리는 동안 외부 스레드가 IsFaulted() 를 폴링하는 구조라 실제로 밟는 경로다.

초기화 순서

설정 → 초기화 → 스레드 순서가 강제되는 이유.

  1. 초기화 전 설정

    SetFramePoolSharable, SetWaitForFrameCopyCompletion, SetImmediateContextGateEnabled. 이 값들은 만들어질 리소스의 모양을 결정한다. 초기화 이후 호출하면 전부 false 를 돌려주고 거절한다 — 조용히 무시하면 설정과 실제 리소스가 어긋난 채로 돌아가기 때문이다.

  2. Initialize(engine, outputIndex)

    렌더 엔진을 외부에서 받으면 공유 모드, 받지 않으면 직접 만든다. 이 선택이 나중에 디바이스 재생성이 가능한지를 가른다.

  3. InitializeDuplication

    어댑터 → 출력(모니터) → DuplicateOutput 순으로 연다. 재연결도 정확히 이 경로를 다시 탄다. 복구 전용 코드를 따로 두지 않은 것은 의도적이다 — 두 벌이면 한쪽만 고치는 일이 생긴다.

  4. CreateFrameResources

    m_duplDesc.ModeDesc 기준으로 슬롯 텍스처 4장을 만든다. 공유 모드면 슬롯마다 NT 공유 핸들과 keyed mutex 를, 복사 완료 확인을 켰으면 EVENT 쿼리를 함께 만든다. 모두 여기서 한 번만 만든다.

  5. 콜백 등록 → StartThread

    스레드가 돌기 시작하면 상태는 Running. 이후 소비자는 GetFramePoolSharedHandle(slot) 로 슬롯 수만큼 핸들을 받아 자기 디바이스에서 딱 한 번 OpenSharedResource1 로 열어 둔다.

설계 판단

공유 텍스처를 매 프레임 여는 것은 또 하나의 드라이버 왕복이다. 슬롯 번호를 핸들에 실어 보내는 이유가 여기 있다 — 소비자는 미리 열어 둔 4장 중 slotId 로 하나를 고르기만 하면 된다.

실패는 전부 Shutdown 으로 되돌린다

Initialize 는 어느 단계에서 실패하든 Shutdown() 을 부르고 false 를 돌려준다. 그래서 Shutdown 의 모든 단계는 대상이 없으면 그냥 넘어가는 형태로 쓰여 있다. 반쯤 초기화된 상태를 남기면 다음 Initialize 가 그 위에 또 쌓는다.

캡처 상태 기계

상태 넷, 그리고 그 사이를 오가는 조건.

Reconnecting 이 무한 재시도인 이유

잠금화면은 몇 시간 지속될 수 있다. 재시도 횟수에 상한을 두면 자리를 비운 사이 세션이 죽고, 돌아왔을 때 화면 공유가 끊겨 있다. 그래서 상한 대신 백오프와 통지 스로틀링으로 비용을 눌렀다.

  • 대기는 50 ms 에서 시작해 2배씩, 500 ms 에서 멈춘다. 보안 데스크톱 전환은 보통 1~2초면 끝나므로 짧게 시작하는 쪽이 복귀가 빠르다.
  • Reconnecting 이벤트는 20회 시도마다 한 번만 올린다. 매번 올리면 긴 잠금화면 동안 호스트 로그가 초당 수십 줄로 넘친다.
  • 대기는 Sleep 이 아니라 정지 이벤트를 함께 기다린다. 그래서 재연결 중에도 StopThread 가 500 ms 에 붙잡히지 않는다.

Faulted 로 가는 유일한 실질 경로

D3D 디바이스 자체가 사라졌는데 그 엔진을 우리가 만들지 않은 경우다. 외부에서 받은 엔진의 디바이스는 다른 사용자와 공유되므로, 여기서 마음대로 다시 만들면 그쪽 리소스가 전부 깨진다. 그래서 되살리지 않고 DeviceRemoved 를 올린 뒤 호스트에 넘긴다.

반대로 우리가 만든 엔진이면 디바이스를 버리고 다시 만들어 캡처를 이어 간다. 이 경우 이전에 나눠 준 텍스처와 공유 핸들은 전부 무효이므로 DeviceRecreated 로 알린다.

콜백을 받은 호스트는 곧바로 다른 스레드에서 인코딩을 시작할 수 있다. 그 작업이 duplication 표면 소유권 반환과 겹치면 같은 immediate context 를 두 방향에서 쓰게 된다. 순서를 바꾸는 것만으로 이 경합이 사라진다 — 락을 하나 더 만드는 대신 순서로 푼 문제다.

발행 순서가 곧 정합성

슬롯을 완성한 뒤에 최신 표식을 옮긴다. 반대로 하면 소비자가 아직 채워지지 않은 슬롯을 "최신" 이라고 믿고 집어 간다. 이 순서 하나가 소비자 쪽 재확인 로직의 전제다.

소비자 — 참조를 먼저 걸고 나서 확인한다

소비자는 반대 방향으로 같은 일을 한다. referenceCount 를 먼저 올려 슬롯 재사용을 막은 뒤, 그사이 캡처가 이 슬롯을 덮어쓰지 않았는지 네 값을 다시 읽어 확인한다. 

for (attempt = 0; attempt < 4; ++attempt) {
    latestId = ReadAcquire64(&m_latestFrameId);
    slotId   = ReadAcquire  (&m_latestFrameSlotId);
    if (latestId <= 0 || slotId < 0)  return {};   // 아직 발행된 것이 없다

    if (slot.status != READY || slot.frameId != latestId)  continue;

    InterlockedIncrement(&slot.referenceCount);       // 먼저 잡고

    if (slot.status == READY && slot.frameId == latestId &&  // 다시 확인
        m_latestFrameId == latestId && m_latestFrameSlotId == slotId) {

        if (!WaitForFrameSlotCopy(slot)) { 참조 반납; return {}; }
        slot.texture->AddRef();
        return { slot.texture, slotId, latestId };
    }

    InterlockedDecrement(&slot.referenceCount);          // 어긋났다. 놓고 재시도
}

재시도를 슬롯 개수만큼만 하는 데도 이유가 있다. 그보다 자주 밀린다면 소비자가 캡처를 따라가지 못하는 것이고, 그건 여기서 더 기다려 해결할 문제가 아니다.

frameId 가 두 가지 일을 한다

  • 새 프레임 판별 — 소비자는 frameId 가 마지막에 받은 값과 같으면 새 프레임이 없다고 본다.
  • ABA 차단 — 슬롯이 재사용되는 사이에 읽힌 낡은 데이터를 걸러낸다. 1부터 단조 증가하므로 같은 슬롯이 돌아와도 번호가 다르다.

잘못된 반납을 흡수한다

예전에는 모르는 slotId 가 들어오면 __debugbreak 로 세웠다. 그런데 디버거를 붙일 수 없는 서버에서도 이 일은 일어난다. 지금은 슬롯을 영구히 잠그지 않는 선에서 흡수하고 카운터로만 남긴다. 

if (InterlockedDecrement(&slot.referenceCount) < 0) {
    InterlockedExchange(&slot.referenceCount, 0);  // 0 으로 되돌리지 않으면
    invalidReleaseCount++;                          // 이 슬롯은 영영 못 쓴다
}

invalidReleaseCount 가 0 이 아니면 소비자 쪽 버그다 — 이중 반납이거나 이 엔진이 주지 않은 핸들이다. 죽지 않고 계속 돌면서 그 사실을 남기는 쪽을 택했다.

디바이스 분리와 공유 텍스처

교착을 없애기 위해 디바이스를 나누고, 나뉜 것을 다시 잇는 방법.

앞서 말한 교착의 해법은 캡처와 인코더에 서로 다른 D3D11 디바이스를 주는 것이었다. (OBS 가 인코더에 별도 디바이스를 주는 것과 같은 구조다.) 그러면 컨텍스트가 독립이라 순환 대기가 성립하지 않는다. 대신 GPU 메모리를 건너 건네줄 방법이 필요해진다.

텍스처를 만드는 방식

desc.MiscFlags = m_framePoolSharable
    ? (D3D11_RESOURCE_MISC_SHARED_KEYEDMUTEX | D3D11_RESOURCE_MISC_SHARED_NTHANDLE)
    : 0;

// 소비자에게 건넬 NT 핸들 — 슬롯마다 한 번만
dxgiResource->CreateSharedHandle(nullptr,
    DXGI_SHARED_RESOURCE_READ | DXGI_SHARED_RESOURCE_WRITE, nullptr, &slot.sharedHandle);

왜 keyed mutex 인가

앱 레벨 락으로는 두 디바이스의 GPU 작업 순서를 맞출 수 없다. 드라이버가 자기 대기 안에서 그 락을 놓아 줄 방법이 없기 때문이다. keyed mutex 는 드라이버가 아는 동기화 객체라서 그 일을 할 수 있다.

왜 NT 핸들인가

구방식(GetSharedHandle)의 핸들은 리소스에 묶여 있어 닫을 수도 복제할 수도 없다. 해상도가 바뀌면 풀을 통째로 다시 만드는데, 그때 소유권과 CloseHandle 을 명시적으로 드러낼 수 있어야 한다.

키를 하나만 쓰는 이유

이 모듈에서 가장 비직관적인 결정

교과서적인 keyed mutex 사용법은 생산자 키와 소비자 키를 번갈아 쓰는 것이다. 이 풀에서는 그게 슬롯을 영구히 죽인다.

이유는 소비 방식에 있다. 이 풀은 latest-only 로 소비되므로 "소비자가 손도 대지 않은 채 버려지는 프레임" 이 정상 경로다. 핑퐁 방식에서는 그때 키가 소비자 쪽에 걸린 채 남고, 그 슬롯은 다시는 생산자에게 돌아오지 않는다.

그래서 키는 0 하나만 쓴다. 어느 쪽이든 아무 때나 잡을 수 있고, 논리적 소유권은 status / referenceCount 가 이미 처리한다. keyed mutex 에게는 디바이스 간 GPU 동기화만 맡기면 되고, 그게 원래 필요한 전부다.

타임아웃은 유한해야 한다

AcquireSync 에 INFINITE 를 주면 방금 걷어낸 교착을 다른 이름으로 다시 만드는 것이다. 100 ms 안에 못 잡으면 이 프레임을 버리고 다음 슬롯을 본다. 우리 쪽 CopyResource 도 예외 없이 뮤텍스를 잡고 한다 — 한쪽만 지키면 지키지 않는 것과 같다.

GPU 복사 완료 확인

CopyResource 는 명령을 큐에 넣을 뿐 완료를 보장하지 않는다. 소비자가 곧바로 읽으면 아직 복사 중인 텍스처를 볼 수 있다. 슬롯마다 EVENT 쿼리를 두고 GetLatestFrameHandle 안에서 확인한다. 

for (;;) {
    { 게이트  hr = context->GetData(slot.copyDoneQuery, nullptr, 0, 0); }  // ← 매 확인마다 게이트를 놓는다
    if (hr == S_OK)     return true;
    if (hr != S_FALSE)  return false;
    ::Sleep(0);   // 복사 한 장은 보통 1ms 미만 — 커널 대기 왕복이 대기보다 비싸다
}

게이트를 루프 밖이 아니라 매 확인마다 잡는 것이 중요하다. 쥔 채로 돌면 그동안 캡처 스레드가 통째로 멈춘다. 이 기능은 SetWaitForFrameCopyCompletion(false) 로 끌 수 있고, 끄면 쿼리 대신 Flush() 로 제출만 하고 지나간다.

캐시 라인 분리

D3D11DuplicateEngine 멤버 배치

멤버를 쓰기 주체와 빈도에 따라 네 덩어리로 나누고 각 덩어리를 alignas(64) 로 띄웠다. 런타임 설정 / 최신 프레임 발행 / 통계 카운터 / 상태.

캡처 스레드가 매 프레임 올리는 통계 카운터와, 외부 스레드가 폴링하는 m_captureState 가 같은 라인에 있으면 폴링할 때마다 무효화된 라인을 다시 가져온다. 반대로 m_latestFrameId 와 m_latestFrameSlotId 는 일부러 같은 라인에 둔다 — 항상 한 쌍으로 쓰이고 한 쌍으로 읽히기 때문이다.

예외를 다루는 세 가지 원칙

  1. 정상 범주는 통지하지 않는다. AcquireNextFrame 타임아웃은 화면이 안 바뀐 것뿐이다. 이걸 이벤트로 올리면 진짜 사건이 묻힌다.
  2. 반복되는 사건은 스로틀링한다. Reconnecting 은 20회마다, DeviceRemoved 는 재시도 사이클당 한 번만 올린다.
  3. 호출자 버그로 죽지 않는다. 잘못된 반납은 카운터로만 남긴다. 대신 그 카운터가 0 이 아니면 반드시 버그라는 것을 문서에 못 박았다.

복구 경로를 테스트하는 법

DebugSimulateAccessLoss() 는 다음 캡처 반복에서 접근 상실이 일어난 것처럼 만들어 재연결 경로를 강제로 태운다. 잠금화면을 실제로 걸지 않고도 상태 전이·백오프·통지 스로틀링을 검증할 수 있다. 운영 코드에서는 호출하지 않는다.

트레이드오프와 한계

고르지 않은 것들, 그리고 고르지 않은 이유.

의도적으로 포기한 것

  • 프레임 순서 보장 — latest-only 소비다. 소비자가 밀리면 중간 프레임은 사라진다. 실시간 스트리밍에서는 이게 맞고, 녹화용으로 쓰려면 풀을 큐로 바꿔야 한다.
  • 슬롯 4개 고정 — 소비자 하나가 한 장을 쥐고 캡처가 다음 장에 쓰는 동안에도 여유가 남는 최소 수다. 소비자가 여럿이거나 장시간 쥐는 구성이면 늘려야 한다.
  • 단일 모니터 — outputIndex 하나를 연다. 여러 모니터를 동시에 캡처하려면 엔진 인스턴스를 여러 개 띄우는 구성이다.
  • 커서·dirty rect 수집 — 코드는 있지만 켜는 API 를 노출하지 않았다. 현재 소비자(인코더)가 쓰지 않는데, 켜 두면 프레임마다 비용만 든다.

남아 있는 것

  • Faulted 에서 스스로 빠져나오지 못한다. 외부 엔진의 디바이스가 복구됐는지 엔진이 알 방법이 없어서 호출자에게 맡겼다.
  • 재연결 백오프 상한(500 ms)이 고정이다. 잠금화면이 길어지면 초당 2회 시도를 계속하는데, 더 늘려도 복귀 체감은 나빠지지 않을 가능성이 있다.

이 모듈에서 얻은 것

가장 값진 교훈은 "정상 경로가 무엇인지 정의하는 것이 곧 설계" 라는 점이었다. ACCESS_LOST 를 오류로 볼지 정상으로 볼지, 소비자가 건드리지 않고 버려지는 프레임을 예외로 볼지 기본으로 볼지 — 이 두 판단이 각각 상태 기계와 keyed mutex 키 설계를 결정했다.

두 번째는 순서로 풀 수 있는 문제에 락을 쓰지 않는 것이다. ReleaseFrame 을 콜백보다 앞세운 것, 슬롯을 완성한 뒤에 최신 표식을 옮기는 것. 둘 다 동기화 객체를 하나도 늘리지 않고 경합을 없앴다.
